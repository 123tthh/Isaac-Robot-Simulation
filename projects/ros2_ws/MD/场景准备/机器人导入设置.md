## 重点两项详解

控制架构是 **ROS 2 + OCS2**，Isaac Sim 的 Drive Type 只影响**仿真器内部关节执行层**，OCS2 在其上层做轨迹规划和补偿。两层职责不同：

```
OCS2 (轨迹规划 + 质量补偿)
        ↓ 关节角度指令
Isaac Sim Drive (执行层)
        ↓
PhysX 物理引擎
```

#### Drive Type 的选择逻辑

|            | Acceleration Drive       | Force Drive          |
| ---------- | ------------------------ | -------------------- |
| 补偿谁来做 | 仿真器自动归一化惯量     | **OCS2 显式建模**    |
| 与OCS2配合 | 可能双重补偿，模型不一致 | ✅ OCS2掌控全部动力学 |
| Sim2Real   | 仿真行为与真实差异大     | ✅ 更接近真实电机特性 |

**OCS2 本身就是基于完整动力学模型的最优控制器**，它已经在代价函数中建模了质量、惯量、重力补偿。如果再让仿真器做 Acceleration 归一化，相当于 OCS2 看到的执行器响应和它建模的不一致，**反而会降低 Sim2Real 精度**。

→ **保留 Force Drive**，让 OCS2 完整掌控动力学补偿。

### 末端下沉补偿怎么做

你的释放窗口数据已经量化了各维度容差，结合 OCS2 的做法：

#### Z 轴下沉（最关键）

你的 Z 窗口是 `1.262~1.273 m`（保守），范围仅 **11mm**，重载时下沉会直接超出窗口。

OCS2 的处理方式：

```
在 task.info 或 cost function 中，
将末端目标 Z 值根据估计质量做前馈偏置：

z_target = z_nominal + Δz(m)

Δz(m) ≈ 由静力学估算：
  Δz = (m - m_nominal) × g × K_compliance
```

其中 `K_compliance` 可以通过在仿真中对不同质量测量实际末端位置来标定。

#### Pitch 补偿

Pitch 窗口 `[8.2, 15.0]°`，重载时末端会因重力矩产生额外 Pitch 偏转。OCS2 的重力补偿项天然处理这个，但需要确认：

- URDF 中各 link 的**质量和惯量**是否准确
- 夹爪 + 托盘的**末端负载质量**是否作为参数传入 OCS2 的动力学模型

### 针对你场景的实用建议

#### 1. 质量估计 → 传入OCS2

由于托盘质量 `[0.96, 1.74] kg` 有较大范围，建议：

```

        ↓
```

### Collision From Visuals → 取消勾选

你的场景中：

- 如果 URDF 已有专用 `<collision>` mesh → 直接用，不需要此选项
- 如果没有 → 勾选会用高面数视觉 mesh 做碰撞体，物理计算量大且不稳定

**建议**：检查 URDF 是否有 `<collision>` 标签。若没有，先在 URDF 中补充简化碰撞 mesh，再导入。

## 关于 Allow Self-Collision 的替代方案

不勾选后，双臂**在仿真层面可以穿模**，但你的任务规划（阶段A左臂让路、避免交叉）本身就在**运动规划层面**避免了双臂碰撞，所以：

> 只要运动规划保证双臂不交叉，不勾选 Self-Collision 在实际任务中完全够用。

如果后续需要更严格的碰撞保护，可以在导入完成后通过 **Physics > Collision Groups** 单独为左臂组和右臂组之间开启碰撞，排除相邻关节对，这比导入时全局勾选更精细可控。

## 一、选哪个 URDF？

## 二、发现的严重问题

分析后发现 **5 个影响仿真正确性的关键问题**：

### 🔴 问题1：14个手臂关节 Link 完全没有惯性数据

这是**最严重的问题**：

| 缺失惯性的 Link                 |
| ------------------------------- |
| left_Link1 ~ left_Link7         |
| right_Link1 ~ right_Link7       |
| left_base_link, right_base_link |

这 16 个 link 没有 `<inertial>` 标签，意味着：

- Isaac Sim 导入后会用 **Default Density（你设的1000）× mesh体积** 自动算质量
- 但 mesh 是视觉用的 `.dae`/`.STL`，体积不精确，算出的质量/惯量**完全不可信**
- **OCS2 的动力学模型如果和仿真里的惯量不匹配，末端补偿会失效**

### 🔴 问题2：trunk_link 惯量疑似单位错误

```
mass = 46.09 kg
Ixx = 66.82, Iyy = 66.67, Izz = 1.50
```

一个 46kg 的躯干（大约 0.5×0.5×0.9m），合理 Ixx 约 **4 kg·m²**，实际值 66.82 是合理值的 **~16倍**。最可能的原因是 CAD 导出时**长度单位用了 mm 而惯量没换算**（差 10⁶ 正好是 mm²→m² 的比例，不完全吻合但在同一量级）。

### 🟡 问题3：所有 RealSense 相机惯量偏大 ~74倍

```
camera_F/B/H/L/R_link: Ixx = 0.003881
期望值（72g, 90×25mm）: Ixx ≈ 0.000052
```

文件里也标注了 `"The following are not reliable values"`。偏差 74 倍，来源于 RealSense 官方 URDF 的占位值，未经修正。

### 🟡 问题4：waist_joint 和 body_joint 的 effort/velocity = 0

```xml
<joint name="waist_joint"> <limit effort="0" lower="-0.5" upper="0" velocity="0"/>
<joint name="body_joint">  <limit effort="0" lower="0" upper="1.5708" velocity="0"/>
```

effort=0 + velocity=0 意味着仿真中这两个关节**没有力矩限制也没有速度限制**，PhysX 会用无穷大处理。实际电机肯定有额定力矩和最大速度。

### 🟡 问题5：left_flange_joint 有重复 `<origin>` 标签

```xml
<origin rpy="0 -1.5707963267949 0" xyz="0.0 0.0 0.0"/>
<origin rpy="0 -1.570796327 0" xyz="0 0 0"/>
```

XML 解析器会取**最后一个**，但这是一个隐患。
